## 2. 各阶段技术方案

### Phase 5 · CI 门禁

**问题**:`.github/workflows/` 空目录。PR 不跑测试,坏代码可直接合并。

**方案**:
```
.github/workflows/ci.yml
├── on: push(main) + pull_request
├── jobs.test:
│   ├── matrix: python 3.12 / 3.14      (项目实际跑 3.14)
│   ├── steps: checkout → setup-python → pip install -r requirements-ci.txt
│   └── run: pytest -q --junitxml
└── jobs.gate:  test 全绿才允许合并
```

同时落 `requirements-ci.txt`,只列测试与运行必需依赖,避免 CI 装全量(含 Flutter/移动端)。

**验收**:workflow 文件语法正确;本地能复现同样的 pip 集合。

---

### Phase 4 · config_loader 去 global

**问题**:3 处 `global`,配置状态隐式可变,热重载行为不可预测。

**方案**:
```python
# 现状
_CONFIG = None
def get_config():
    global _CONFIG
    if _CONFIG is None: _CONFIG = _load()
    return _CONFIG

# 目标:显式生命周期 + 不可变快照
@dataclass(frozen=True)
class ConfigSnapshot:  ...
@lru_cache(maxsize=1)
def _load_cached() -> ConfigSnapshot: ...
def get_config() -> ConfigSnapshot: ...        # 读
def reload_config() -> None: _load_cached.cache_clear()   # 显式失效
```

**关键点**:提供公开的 `reload_config()`,把"何时失效"从隐式全局变成显式调用。不改变现有调用方的读接口。

**验收**:`test_config_loader.py` 全绿;`reload_config()` 有测试覆盖。

### Phase 2 · pipeline 合并

**问题**:`pipeline.py`(v1,592 行,20 处 `except`)与 `pipeline_v2.py`(v2,611 行)并存,10 个文件同时引用。两者并非复制(实文本重复仅 6 行),而是两代实现,调用方混用。

**方案**:建立包结构,单一公共入口:
```
lib/pipeline/
├── __init__.py     统一导出 PipelineV2 + 兼容别名 PipelineRunner
├── v2.py           (现 pipeline_v2.py 主体,不加改动搬迁)
├── legacy.py       PipelineRunner,@deprecated,内部转发
├── state.py        ChapterCheckpoint / CheckpointDoc / StageCheckpoint / StageState
└── errors.py       PipelineError + 错误码
```

**迁移纪律**:
1. 先建包 + 兼容导出,**不删任何实现**
2. 逐个调用方切到 `lib.pipeline` 统一入口
3. 全量测试每切一批
4. 调用方全部切换且测试绿,**才**给 legacy 加 deprecation warning
5. 下一版本再删

**关键点**:不搞一次性重写。v2 是否该完全取代 v1,需要业务判断(是否有 v2 尚未覆盖的能力),不能凭行数决定。

**验收**:全量测试绿;`grep -r "from lib.pipeline_v2\|from lib import pipeline_v2"` 为空。

### Phase 3 · 异常收敛

**问题**:`except` 密度:
```
lib/pipeline.py        28 处
lib/chapter.py        15 处
novel.py              13 处
lib/review_service.py 12 处
lib/pipeline_v2.py    12 处
```
大量 `except Exception: pass` 或宽泛捕获,故障静默,排查时看不到根因。

**方案**:
```python
# 1) 错误分类(lib/pipeline/errors.py)
class PipelineError(Exception):
    def __init__(self, msg, *, stage, book, chapter, cause): ...
class TransientError(PipelineError): ...    # 可重试
class PermanentError(PipelineError): ...    # 不可重试,直接失败

# 2) 重试策略
@retry(times=2, on=(TransientError,), backoff=1.5)
def run_stage(...): ...

# 3) 收敛规则(逐条人工判定,不做机械替换)
✅ 可重试的网络/IO 异常  → TransientError + 重试
✅ 业务校验失败          → PermanentError,带明确 message
✅ 未知异常              → 记录完整 traceback 后抛出,不吞
❌ 裸 except: pass       → 消除
❌ 宽泛 except 降级返回   → 记录 warning + 明确失败态
```

**纪律**:
- **逐条**判定,不写脚本批量替换。每处 `except` 都要回答"这里失败应该怎么办"
- 配套加测试:每个收敛点补一个"该失败时确实失败"的用例
- 一次只改一个模块,`pipeline.py` 优先(28 处)

**验收**:新增"失败路径"测试;`grep -c "except Exception:\s*$" ` 后跟 `pass` 的数量归零。
